MALAYALAM HANDWRITING RECOGNITION APP — PLAN RECAP
====================================================
Last updated: 2026-08-21

PROJECT OVERVIEW
-----------------
A CNN trained on handwritten Malayalam characters, wrapped in a web app.
Users are shown a target character, draw it on a canvas with a pencil tool,
submit it, and get told whether they were correct — and if not, what
character they actually drew (confidence score included). Modeled after a
reference Devanagari/Sanskrit practice app (DevanagarAI).

Intended for portfolio/resume use — not just a private local demo. This
matters for how data provenance and licensing are handled (see below).


1. DATA
--------
Dataset: Amrita_MalCharDb (Malayalam Character Image Database), hosted on
TC-11 (IAPR Technical Committee 11 reading-systems dataset registry).

Confirmed specs:
- 85 character classes: vowels, consonants, half-consonants, and modifiers
  (a domain-chosen taxonomy — broader than "core letters only", narrower
  than full conjunct explosion. Use their scope as-is rather than
  re-deriving one.)
- 77 writers total (60 female, 17 male; ages 20-55; minimum graduation-level
  education)
- Predefined writer-independent split: 59 writers for train/validation,
  18 writers held out for test. KEEP this split intact — do not reshuffle
  samples across it, since writer-independence is what makes test accuracy
  meaningful.
- Images: pre-binarized (pure black/white, no grayscale/antialiasing),
  32x32 pixels, stored as flattened 1024-dim vectors in CSV files (not
  image files). Reshape each row to 32x32 with numpy when loading.
- Collection method: scanned ballpoint-pen-on-paper (not digital stylus),
  processed with active contour models + Otsu thresholding.

Known limitations to keep in mind / eventually note publicly:
- Writer pool skews heavily female and is adults-only with formal
  education — may not generalize as well to children's handwriting or
  less "neat" styles.
- Scanned pen-on-paper strokes differ from mouse/touch canvas strokes
  (natural width variation vs. uniform digital strokes) — handle via
  preprocessing (see Webapp section).

Note: this is distinct from another Malayalam academic dataset referenced
during research — a 44-class, 228-writer, scanner-digitized set from a
related ScienceDirect paper. Different release, same general research
community. Be clear in documentation about which one was actually used
(Amrita_MalCharDb, 85 classes / 77 writers).

Licensing / attribution:
- TC-11 gives a named creator and explicit citation format:
  "Manjusha K, Malayalam Character Image Database (Amrita_MalCharDb)"
- Cite this exactly in the README. Link the TC-11 dataset page.
- Do NOT commit the raw dataset (CSV files) to a public repo — add to
  .gitignore, same as any large third-party data folder. Note in the
  README where to download it for reproduction.
- Ship only your own code and the trained model weights publicly — a
  model derived from the data is a much lower-risk category than
  redistributing the source files themselves.


2. MODEL
---------
Framework: PyTorch.

Approach:
- Start with a small CNN baseline (a few conv/pool blocks, batchnorm,
  dropout) rather than reaching for a big pretrained backbone immediately.
- Use the dataset's predefined writer-independent split for train/val/test.
- Add data augmentation (small rotations, elastic distortion, stroke-width
  jitter) since handwriting datasets are small relative to real-world
  handwriting variance.
- Review the confusion matrix, not just top-line accuracy. Expect visually
  similar Malayalam letter pairs to cluster as confusions — this is a
  property of the script, and it tells you where to prioritize attention
  (more data, or accepting the limitation) rather than necessarily
  indicating a bug.


3. TRAINING ENVIRONMENT (DOCKER)
----------------------------------
Purpose: explicitly scoped to training reproducibility and to build Docker
experience — NOT used for serving/inference in production. This keeps it
consistent with the "no backend" deployment architecture (see below).

What goes in the image: pinned Python/PyTorch (and CUDA, if training on
GPU) versions, training code and dependencies.

What does NOT go in the image: the dataset or model checkpoints. Mount
these in/out via volumes (-v) so the image stays small/generic and
checkpoints survive after the container exits.

Two container patterns worth practicing (both are good Docker learning
exercises):
- Interactive container: mounted code, live iteration (e.g. Jupyter or
  shell inside the container).
- Hermetic container: `docker run` executes a finalized train.py end to
  end with no manual steps, producing an identical checkpoint every time.

The single artifact that crosses OUT of Docker into the rest of the
pipeline: model.onnx (plus labels.json, see below).

OPEN DECISION: CPU-only training (simpler Dockerfile) vs. GPU/CUDA training
(more involved — needs a CUDA-compatible base image, nvidia-container-
toolkit, and the --gpus flag; a genuine Docker learning opportunity but
adds real setup complexity). Not yet decided.


4. EXPORT (PYTORCH -> ONNX)
------------------------------
- Export trained PyTorch model to ONNX (torch.onnx.export).
- Verify the ONNX model's outputs match the original PyTorch model's
  outputs on a handful of test images before trusting it downstream —
  op-version mismatches or eval-mode differences (e.g. batchnorm/dropout)
  can silently change behavior on export.
- Also export labels.json: a class-index -> Malayalam glyph (+
  transliteration) mapping, generated directly from the training script's
  class ordering so it can never drift out of sync with the model.


5. INFERENCE ARCHITECTURE — CLIENT-SIDE ONLY, NO BACKEND
------------------------------------------------------------
Decision: use ONNX + onnxruntime-web. All inference (preprocessing +
CNN forward pass) runs inside the visitor's browser via JS/WASM. No
server-side application logic ever touches a user's drawing.

What "no backend" means concretely:
- A backend = code running on a machine you control that computes a
  result specific to each request's input (e.g. a FastAPI /predict
  endpoint). This project has none of that.
- What IS still needed: a plain static file server to hand the browser
  the HTML/JS/model.onnx/labels.json files. This has zero application
  logic — same bytes served to everyone, comparable to a librarian
  handing out books vs. a tutor solving your specific homework.

Tradeoff of this choice: no server cost, instant predictions (no network
round-trip), but bound by whatever compute the visitor's device has, and
updating the model means shipping a new file to every visitor rather than
swapping a file on one server.


6. WEBAPP (LOCALHOST DEMO)
-----------------------------
Structure: static site.
- index.html: canvas + controls (Pencil, Eraser, Reset, Submit, Skip,
  Next Question — matching the reference app's layout)
- Drawing module: pointer/touch event listeners for canvas strokes
- Inference module: preprocessing + onnxruntime-web session + prediction
- Assets served alongside the JS: model.onnx, labels.json

Critical preprocessing requirement (train/serve consistency): the canvas
capture pipeline MUST reproduce the training data's format exactly —
crop to the ink's bounding box, resize to 32x32, and BINARIZE (threshold
to pure black/white — the source dataset has no antialiasing/grayscale).
Getting this wrong is the most common reason these apps work in the
notebook but feel broken in the browser.

Stroke-width consideration: since training images come from scanned pen
strokes (not digital stylus), canvas pencil strokes may need a deliberate
minimum thickness (or a slight blur/dilation before downsampling) so they
don't thin out to near-invisibility once resized to 32x32.

Running it: no build step is required in principle, but SOME local HTTP
server is required even for a demo — opening index.html directly as a
file:// URL will fail because fetch() (needed to load the WASM runtime and
the .onnx file) is blocked under file:// in Chrome. Options: `npx serve`,
Python's `http.server`, or a dev server like Vite.

OPEN DECISION: vanilla JS + CDN-hosted onnxruntime-web (zero build step)
vs. npm + Vite (bundled, closer to a "real" production setup, easier
dependency pinning). Not yet decided.

Explicitly out of scope for this demo phase: authentication, a database,
persistence of user attempts, HTTPS, real hosting.


7. STRETCH GOAL / V2
----------------------
Once the app works end to end: use the app's own canvas tool to collect
some user-drawn, self-labeled training data. This sidesteps third-party
licensing questions entirely for that slice of data, and — given the
portfolio framing — makes for a stronger project story ("I built the
model, the app, AND part of the data collection pipeline") than relying
solely on a downloaded dataset.


OPEN DECISIONS SUMMARY
------------------------

2. Vanilla JS + CDN vs. npm + Vite for the frontend build
